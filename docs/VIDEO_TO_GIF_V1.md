# 视频转 GIF（Phase 1）交付记录

本文件记录 2026-09 「完善视频转 GIF」的实现范围、交互审查结论、验证结果与未完成项。
只做 Phase 1（视频转 GIF），Squoosh 单图压缩入口尚未开始，属 Phase 2。

本轮（第二轮）在上一轮基础上只加两件事：**四种输出倾向**与**主动「计算预览」**，并把所有
异步操作的代次校验补齐；没有新建第三套 GIF 生成器，没有开始 Phase 2，也没有改 Windows sidecar。

## 一、真实任务链

```txt
1. 从首页或侧栏进入「视频转 GIF」
2. 选择一个 MP4 / MOV
3. 拖动时间轴截取一段区间，把播放头停到想检查的那一帧
4. 选输出倾向（均衡 / 帧率优先 / 画质优先 / 自定义），确认帧率与期望宽度
5. 点击「计算预览」：看真实输出单帧 + 明确标为「估算」的体积范围，必要时看建议宽度/缩短提示
6. 点「开始处理」，等待真实编码（能复用的有效采样会直接复用）
7. 拿到 ≤ 8,000,000 字节的 GIF，或看到明确的失败说明
```

第 4–6 步是本轮改动：**参数变化只让旧结果失效，只有点击「计算预览」才会启动 FFmpeg**。

## 二、交互审查结论

按 `skills/lightweight-workbench-ux-audit/SKILL.md` 的固定输出：

### 用户真实任务链

见上。核心动作只有「选一段、定尺寸、拿一个不超过 8 MB 的文件」。

### 当前主要问题

1. 该工具同时挂着「普通模式 / 模板模式」两套入口，模板模式又要求模板 PNG、占位色、色键、填充方式，属于「批量模板 GIF 合成器」的能力，放进单视频入口只会让用户以为要配模板。
2. 文件选择器 `multiple: true`，并且 `addFiles` 会把多个文件追加进「任务队列」，与 v1「只支持单个视频」直接冲突；队列里只有第一个视频有预览，行为不自洽。
3. `mode` 变量被固定为 `'plain'` 之后，模板模式的整块模板与状态成为不可达代码，其中还保留一条用户永远看不到的提示。
4. 字节预算写的是 `7.8 * 1024 * 1024`（MiB 语义、且序列化成 JSON 浮点），与实际承诺的十进制 8 MB 不一致；Rust 侧 `u64` 字段直接拒绝该浮点，请求会整条解析失败。
5. 历史实现每次重试都会先把编码结果 `rename` 到用户目标路径再做大小校验，重试耗尽后会把超限 GIF 留在输出目录。

### 建议删除

- 模板模式的整块 UI、`mode` 状态与相关模板/色键状态（已删除）。
- 只服务模板模式的 `GifToolMode`、`ChromaKey*`、`TemplateGifComposeRequest`、`TemplatePreviewRequest`、`CHROMA_COLORS`、`DEFAULT_CHROMA_KEY`（已删除）。
- 这些类对应的孤立 CSS（已删除）。
- 多文件入队路径（已改为「重新选择即替换当前视频」）。

### 建议保留

- 时间轴截取、双预览、压缩偏好、高级下限——都是这一条任务链必需的精调方式。
- `batch-template-gif` 模块本身不动，模板合成继续留在它自己的入口。

### 交给成熟库的部分

- GIF 编码与调色板：继续用随包 FFmpeg（`palettegen` / `paletteuse`，两遍）。不自研编码器。
- 文件选择、目录选择、保存、打开目录：继续走 Tauri dialog / fs 官方插件。

### 最小修改方案

删掉模板模式与批量入队，把「单视频」写进代码而不是只写在文案里；把字节上限统一成十进制 8,000,000 并在 Rust 侧独立兜底；只在真实编码字节数通过校验后才发布文件。

### 明确不做

- 不做批量队列、不做模板合成、不做色键、不做多轨时间轴、不做剪辑。
- 不做 GIF 以外的格式导出，不做自研编码器。
- 不改 `batch-template-gif`、水印、Logo/CPR、导出中心、更新/签名/镜像链路。
- 不改隐藏的 `src/gif-media/` 旧窗口模块（本轮只让新入口可达，不再新增第二套实现）。

### 本轮补修（按用户逐条要求）

1. **超限不再立即终止**：原来第一次超过 8,000,000 字节就判 `Fail(HardLimit)`；现在只要还有缩宽空间就继续缩宽，只有到下限或两次完整编码用完才明确失败。
2. **替换规则**：只有真正在跑的转换才拒绝更换视频；`waiting` 状态重新选片会替换。替换时立即作废旧的探测/预览，并用 generation token 丢弃换代后回来的旧异步结果。
3. **规则对齐独立 GIF 工具**：FPS 是用户硬约束，压缩绝不改动；超限只缩宽度或明确停止；短样本分析与正式生成同源；完整编码最多两次（详见第三节差异表）。没有新建第三套算法或任务框架，也没有照搬模板合成管线。
4. **非覆盖发布**：不再依赖 `next_available_path` 的「提前不存在」，改为硬链接原子发布 + `_2`/`_3` 序号回退，并写明文件系统适用条件（见第三节）。
5. **行为测试**：真实 FFmpeg 跑通「首次超 8 MB → 缩宽达标且帧率/时长不变」「不可达预算失败无残留」「同文件不覆盖 + 同名并发」「取消只有一个终态」；前端用 jsdom 挂载真实组件验证「未开始可替换」「旧探测结果不回写」。测试强度用反向改坏旧逻辑验证（3 条用例立刻失败）。

### 本轮：四种倾向 + 主动「计算预览」的交互审查

按同一份 `skills/lightweight-workbench-ux-audit/SKILL.md` 的固定输出，只记录本轮增量的结论。

#### 用户真实任务

「这段视频选一段，做成一个不超过 8 MB 的 GIF，并且先让我确认画面和体积大概多少。」
用户真正要判断的只有两件事：**这一帧够不够清楚**、**这个体积预算会不会爆**。

#### 当前主要问题（改前）

1. 「均衡 / 优先清晰 / 优先流畅」三个标签只影响超限时缩宽的幅度，用户看不出它们的实际差别；标签本身不能告诉他帧率会是多少。
2. 输出宽度只写在输入框里，用户不知道「期望宽度」和「预算建议宽度」的区别，也没有任何主动确认体积的手段。
3. 旧的输出预览是 **350 ms debounce 自动**触发的：拖时间轴就会连续启动 FFmpeg，既浪费机器，也让用户以为那是「正式结果」。
4. 自动预览只给一张 GIF 图，没有体积估算、没有输出尺寸/帧率/时长说明，不能支撑「要不要开始处理」这个决定。
5. 异步路径仍有 await：`addFiles` 里 `await cancelPreviewTask(...)` 之后继续写状态，连续换素材时可能用旧代次回写新素材。

#### 建议删除

- 「均衡 / 优先清晰 / 优先流畅」选择器（被四种倾向替代，不同时保留两套）。
- 350 ms debounce 的 `scheduleOutputPreview` / `generateOutputPreview` / `previewTaskId` / `previewGeneration` 全套自动预览状态。
- 高级面板里的独立「最低输出宽度」（改为：预设倾向由规则推导并明示，自定义倾向才让用户填）。
- 单帧预览旁的「体积」字样（单帧不参与体积推算，避免误导）。

#### 建议保留

- 时间轴截取、播放头、原片预览、单视频替换规则。
- 「最多两次完整编码，帧率与截取时长不变」的既有规则与文案。
- 非覆盖硬链接发布、取消/失败清理。

#### 交给成熟库的部分

- 单帧提取、短样本编码、调色板：继续用随包 FFmpeg，同一个 `build_gif_encode_args`；没有引入新的编码器、没有自研估算算法。
- 视频尺寸/时长探测：继续用随包 FFprobe（`video_size` / `duration_seconds`）。
- 图片显示：Tauri asset 协议 + `asset_protocol_scope().allow_file()`（官方运行时 API），不新增本地 HTTP 服务。

#### 最小修改方案

后端加一个显式的 `analyze_gif_media_task`：同一 FFmpeg 参数构造器编一段 320px / ≤2s 的短样本，
把字节数按 **片段时长 ÷ 样本时长** 与面积比换算成整段估算，并用同一份样本给建议宽度；
同一张请求里的 `sample` 提示经后端签名校验后才被正式生成复用。
前端删掉自动 debounce 预览，换成「计算预览」按钮 + 结果面板，四种倾向只驱动一个真实的帧率控件与
宽度规则；所有 await 之后都校验代次。

#### 明确不做

- 不做第三套 GIF 生成器、不做批量/模板/颜色槽、不改 `batch-template-gif` 与水印/Logo/发布/签名/更新链路。
- 不新增通用缓存框架（采样复用只是「同一请求内的一次签名校验」）。
- 不擅自更换调色板算法或编码器，不加复杂编码参数面板。
- 不把「估算」写成达标保证；不静默把用户填的期望宽度换成建议宽度。

### 包体影响

无新增依赖。前端 `dist` 合计 1,666,051 B / 25 文件（改造前 1,666,139 B / 25 文件），净变化 −88 B；主 chunk 718,274 B（前 713,799 B，+4,475 B，含新增入口与文案），主 CSS 135,025 B（前 134,800 B，+225 B）。未新增 WASM、Worker、字体或运行时。

本轮补修后：`dist` 1,665,517 B / 25 文件（较上一轮 1,666,051 B 减少 534 B，来自删除「最低帧率」「允许强压缩」两个控件及其文案），主 chunk 718,274 B、主 CSS 135,025 B 不变；无新增依赖。

四种倾向 + 计算预览后：`dist` 1,679,093 B / 25 文件（较 1,665,517 B 增加 13,576 B），主 JS chunk 726,287 B（前 718,274 B，+8,013 B）、主 CSS 135,025 B 不变；仍无新增依赖、无 WASM/Worker/字体/运行时。

### 验收场景

1. 首页卡片与侧栏都能进入，页头显示「视频转 GIF」。
2. 一次只持有一个视频；再次选择会替换，转换进行中不允许替换。
3. 正常短视频导出成功，文件真实字节数 ≤ 8,000,000。
4. 预算不可达时明确失败，输出目录里没有任何残留文件。
5. 取消任务后不留下临时文件，也不产生矛盾的完成/失败事件。
6. 四种倾向各自带出真实帧率（10 / 15 / 8 / 自定义），切换时帧率控件立即变化，期望宽度仍是真实数字。
7. 只改参数不会启动 FFmpeg；点一次「计算预览」才启动一次，计算中再点不会重复启动。
8. 计算预览给出真实输出单帧、输出宽高/帧率/时长、标为「估算」的体积范围，以及「仅供参考」的建议宽度或缩短提示。
9. 参数/素材/区间/模式变化后旧结果立即失效并作废在跑的分析；晚到的旧结果不回写。
10. 连续换 B、C 两个素材且响应乱序时，最终界面只描述 C。

## 三、实现要点

### 后端（`src-tauri/src/media.rs`）

- `MAX_GIF_BYTES = 8_000_000`：Rust 侧独立硬上限（十进制），客户端传来的 `targetBytes` 只能更小，不能放大。
- `flexible_u64`：`targetBytes` 接受整数或浮点 JSON 并取整，历史前端发来的 `8178892.8` 不再导致整条请求失败。
- `gif_step_outcome(...)` → `Publish | Retry | Fail(BudgetUnreachable | NoRoomToShrink)`：重试循环里唯一的裁决点，纯函数、可单测。
- 临时文件命名 `.{stem}.{pid}-{taskid}-{seq}.{slot}.tmp.gif`，并在参数里显式写 `-f gif`：不再依赖 FFmpeg 从扩展名猜 muxer（`.gif.part` 的猜测会直接失败），且每个任务、每次尝试的临时文件互相隔离。
- 参数构造与输出路径彻底分离：`build_gif_encode_args` 只产出编码选项、不接收任何输出路径，由 `gif_encode_args_with_temp` 追加 `-y` + 临时路径。这样 FFmpeg 永远只看到临时文件一个输出，用户目标路径不可能被提前写入。
- 取消走 `GifEncodeError::Cancelled` 直接返回，不再在 `Cancelled` 之后再补一条 `Failed`；取消/失败/完成三条路径各自只发一条终态事件。
- `format_file_size` 改为十进制（`/1_000`、`/1_000_000`），8,000,000 B 显示为 `8.0 MB`。
- `analyze_gif_media_task`（本轮新增，`async` + `spawn_blocking`）：显式「计算预览」的唯一入口。
  一次拿到 ①选定时间点的真实单帧（`-ss <t> -i 源 -vf "fps=<fps>,scale=<期望宽度>:-2" -frames:v 1`，
  PNG 写入系统临时目录 `brand-material-gif-analysis/`）②短样本编码（`gif_sample_plan`：≤320px、≤2s）
  ③整段体积估算与建议。分析期间 FFmpeg 子进程注册进 `MediaTaskRegistry`，并额外登记 cancel token，
  因此两个子进程之间的空档也能被现有的「取消」命令中止；取消/失败会删除分析残留，成功时短样本也立即删除。
  单帧路径通过 `asset_protocol_scope().allow_file()` 加入运行时 asset 作用域（官方 API），没有放宽其他路径。
- 估算规则（取代上一轮的 `estimate_gif_width`）：
  `gif_bytes_per_second(sample_bytes, sample_seconds, sample_width, width)`（面积比）→
  `gif_estimate_full_bytes(...)`（再乘 **片段时长 ÷ 样本时长**）→
  `fit_width_for_budget(...)`（闭式解出预算内宽度）→ `gif_estimate_range(...)`（±20% 区间）→
  `gif_analysis_advice(...)`（先建议宽度；连最低宽度都放不下时才建议缩短片段）。纯函数、可单测。
  **短样本字节数不再被当成整段体积**，这是上一轮遗留的第 (1) 个问题。
- 采样复用：`gif_sample_plan`（宽度/时长）与 `gif_sample_signature`（源路径 + 文件长度 + fps + preset +
  起点 + 样本几何）由分析与正式生成共用；正式生成只在签名完全一致时复用，否则自己重新采样。
  这不是缓存框架：没有跨请求存储，只有「同一次请求里带过来的一条提示」。
- `GifMediaOptions` 用 `mode`（`balanced|fps|quality|custom`）+ `min_width` + 可选 `sample`；
  `validate_gif_inputs` 校验 mode 白名单、`min_width ∈ 1..8192`、`min_width ≤ width`，
  `validate_request` 再额外要求输出目录存在（分析只写临时目录，所以不需要它）。
- `video_width` → `video_size`（同时返回宽高，`scaled_height` 复算 `scale=w:-2` 的输出高度）。

#### 压缩规则：与独立 GIF 工具对齐后的差异

旧实现与本轮实现的关键差异（用户硬约束优先于「压得下去」）：

| 维度 | 旧实现（本轮已替换） | 现实现 |
| --- | --- | --- |
| 帧率 | `reduce_gif_params` 每轮可自动下调 FPS（8–9 轮宽度+帧率联动） | FPS 是用户硬约束，压缩**绝不**改动；也不再有 `minFps` 参数 |
| 超限时 | 首次超过硬上限即 `Fail(HardLimit)`，直接终止 | 只要还有缩宽空间就继续，不立即终止 |
| 编码次数 | 最多 8–9 轮 | 短样本分析 1 次 + 完整编码最多 2 次（`MAX_GIF_FULL_ENCODES = 2`） |
| 分析样本 | 无 | 短样本走**同一个** `build_gif_encode_args`（只改宽度与时长，FPS 不变），用 `fit_width_for_budget` 预测首次宽度；可复用「计算预览」的有效采样（签名一致时） |
| 体积估算 | 无 | 短样本字节数 × (整段时长 ÷ 样本时长) × 面积比，给出 ±20% 的**估算区间**；不再把样本字节数当整段体积 |
| 预览触发 | 350 ms debounce 自动重算 | 只有点击「计算预览」才启动；参数变化只失效旧结果 |
| 停止条件 | 轮数耗尽 | 已到宽度下限仍超限 → `Fail(NoRoomToShrink)`；还有缩宽空间但两次完整编码用完 → `Fail(BudgetUnreachable)` |
| 输出倾向 | 三档「清晰/均衡/流畅」，只影响宽度 | 四种倾向（`balanced` 0.92 / `fps` 0.85 允许更大幅度缩宽 / `quality` 0.97 保护分辨率 / `custom` 0.92），**只影响宽度校正的幅度**，帧率仍由用户在倾向档位内选择 |

`next_gif_width` 只做一件事：按面积模型 `w × sqrt(budget × safety / actual)` 求下一次宽度，并保证**严格变小**且**不低于下限**；到下限返回 `None` 而不是再编一次相同画面。失败消息里写明尝试次数、下限、十进制体积与原始字节数、帧率保持不变、截取时长不变，以及「本次产物已删除，未写入输出目录」。

本轮**没有**照搬模板合成管线（`TemplateCompressionOptions` 仍是 MiB 语义、多输出、多任务），也没有为它新建第三套算法或任务框架：单视频单输出继续使用 `GifTaskHost` + `run_gif_task_loop` 这一条链路。

#### 非覆盖发布（`persist_gif_final`）

`next_available_path` 只是**预检**，不是原子占位：它返回之后到真正落盘之间，同名文件可能被别的进程或另一个任务创建，而 macOS 上 `fs::rename` 会**直接覆盖**已存在文件。因此发布不再用 `rename`：

1. 先在**目标目录**创建唯一临时文件（`create_new(true)`，同名即失败），写完后 `flush()` + `sync_all()`；
2. 用 `fs::hard_link(temp, 目标名)` 发布——硬链接在目标已存在时返回 `AlreadyExists`，不会覆盖；
3. `AlreadyExists` 时依次尝试 `_2`、`_3`… 直到成功；
4. 成功后再删除临时文件；任何其他错误都删除临时文件并明确报错。

因此**不凭「提前判断文件不存在」声称保证不覆盖**，而是让「目标已存在」这个事实由文件系统在落盘那一刻裁决。

适用条件：硬链接要求目标目录与临时文件同卷、且文件系统支持硬链接。APFS / HFS+ / NTFS / ext4 支持；exFAT / FAT32 与部分网络挂载不支持——此时宁可明确失败（错误里提示「该文件系统可能不支持硬链接」），也不回退到会覆盖既有文件的 `rename`。

### 前端

- `src/gif-tool/types.ts`：`HARD_LIMIT_BYTES = 8_000_000`、`TARGET_FILE_BYTES = 7_800_000`，`formatFileSize` 同步十进制；删除 `minFps` 与 `allowStrongCompression`（FPS 固定后它们无法产生任何效果，留着就是骗人的控件）。

- `src/gif-tool/GifTool.vue`：
  - 只有**真正在跑**（`runningTask`）的转换才拒绝更换素材；任务还在 `waiting` 时重新选片会直接替换。
  - 四种倾向是唯一的策略选择器（旧「清晰/流畅/均衡」已删除）。切换倾向会**立即**把帧率控件改成该倾向的实际默认档位；期望宽度始终是真实数字（探测后自动填入素材宽度）。预设倾向的下限由 `presetMinWidth` 推导并在文案里明示，只有「自定义」才让用户填最低允许宽度。

  - `invalidateAnalysis`（参数/区间/模式/播放头变化、换素材、卸载）立即清空结果、`analysisTicket += 1`，并通过现有 `cancelTask` 作废在跑的分析；晚到的旧结果在 `await` 后按 ticket 丢弃，不写 `analysis`/`loading`/`error`。

  - 正式生成请求使用与预览同一组 `fps/width/startSeconds/endSeconds/mode/minWidth`，并在结果仍然有效时带上 `sample` 复用采样。

#### 本轮修掉的一个自造回归（记录在案）

第一版改动删掉了 `run_gif_encode_with_progress` 里「把最终输出路径从参数里过滤掉」的逻辑，但调用方仍然把最终路径交给 `build_gif_encode_args`，于是 FFmpeg 收到两个输出：

```
... -t 1.25 -filter_complex ... -f gif -progress pipe:1 -nostats <目标.gif> -y <.临时.tmp.gif>
```

实测后果有两条：一是目标路径在体积校验之前就被写入（正是本需求禁止的行为）；二是 `-t` 只约束第一个输出，第二个输出没有时长上限，于是被检查体积的那个临时文件对应的是「从截取起点到文件结尾」的画面，而不是用户选的片段。现在参数构造不再接收输出路径，只有一个输出，且必然是临时文件。

## 七、GIF 原片 / 参考帧 / 最终预览修正（2026-10-19，独立改动）

### 改前的功能缺口

1. 原片与参考帧都用前端手写的 `asset://localhost/<encodeURIComponent(path)>` 拼地址，没有走 Tauri 官方转换；拖入窗口的文件不像文件选择器那样被 dialog 插件自动授权，asset 协议会 403，画面空白且没有任何提示。
2. `<video>` 没有原生控件、没有加载后就位、没有错误反馈，`:currentTime` 这种属性绑定也不会真正 seek；用户无法播放原片或按画面定位参考帧时刻。
3. 参考帧失败与体积分析共用一块状态：帧加载失败时没有任何反馈，用户也分不清「帧没显示」和「分析没结果」。
4. 导出成功后没有任何最终 GIF 预览：任务卡只有文件名与字节数，用户无法确认动画是否正确；也没有任何「真实文件」的可视证据。

### 修正内容

- **官方 asset 转换**：新增 `src/gif-tool/assetUrl.ts`，统一用 `convertFileSrc(path, 'asset')`；浏览器 / jsdom 等没有 Tauri 运行时的环境返回空字符串并显示「当前环境无法预览」，不伪造地址。
- **按单文件运行时授权**（Rust）：`probe_media` 在确认文件存在后调用 `asset_protocol_scope().allow_file(input)`，放行用户本次选择或拖入的这一个视频；GIF 成功发布后通过 `GifTaskHost::authorize_preview` 只放行刚写入的那一个最终文件。`tauri.conf.json` 的静态 scope 仍为空，没有放宽全盘读取。失败、取消、超限路径不会产生任何授权。
- **原片播放**：`<video controls preload="metadata">`；`loadedmetadata` 后就绪并定位到时间轴播放头；用户拖动播放器进度条触发 `seeked` 时时间轴跟随并让旧参考帧失效；`error` 时明确提示「文件可能已被移动、删除或未获得读取授权；不影响计算预览与导出」。播放本身不会自动启动任何分析。
- **参考帧与体积分析分开显示状态**：`frameStatus`（idle / loading / ready / error）独立于分析结果；帧加载失败只显示「参考帧加载失败…这不改变右侧的参数与体积结果」，分析数字保持不变；帧就绪时说明「参考帧为 RGB 单帧，最终 GIF 会按 256 色调色板量化，颜色可能略有差异」。
- **最终 GIF 预览**：完成事件后用**真实导出文件**（不是暂存副本）和官方 asset URL 显示动画；`load` 事件读取 `naturalWidth/naturalHeight` 得到真实像素尺寸，字节数来自完成事件的真实 `outputBytes`，并显示实际写入路径。预览失败只提示「文件已导出，预览失败。」并保留路径，任务状态保持 `success`，不调用取消、不清理任何文件。只展示当前仍在任务列表里的 `taskId`，晚到的旧完成事件不会显示。
- 手动「计算预览」规则保持不变：只有点击按钮才启动 FFmpeg；参数、区间、播放头、换素材只让旧结果失效。

### 交互审查结论（只读阶段，先于改动）

#### 用户真实任务链

```txt
导入视频 → 定位并截取片段 → 选择压缩倾向 → 计算 GIF → 放大检查结果 → 保存
```

#### 当前主要问题

1. 页面是「预览 + 参考帧 + 最终预览 + 任务卡 + 表单」的纵向堆叠，主预览不在固定位置，任务状态散落在多张卡片里；用户必须滚动才能看到主操作。
2. 主操作被拆成「计算预览」（只出 PNG 参考帧 + 估算）和「开始处理」（直接写导出目录）两条互不对应的路径；计算阶段没有任何真实 GIF，也没有可放大的结果。
3. 计算阶段被要求先选导出目录，与任务链（先算、看结果、再保存）相反。
4. 同一个动作存在多套入口：导入按钮 + 拖放区 + 「当前视频」卡片；模式选择 + 帧率 + 宽度分散在不同卡片。

#### 建议删除

- 旧的两栏堆叠布局与 `.gif-tool-layout` 滚动容器。
- 任务卡列表、导入拖放区、「当前视频 / 已选择的视频 / 1 个视频」等重复素材信息。
- PNG 参考帧预览、体积估算卡、旧的「计算预览 / 开始处理」双按钮与导出目录选择器（计算阶段）。
- 旧的分析代次/参考帧/最终预览状态，改为单一「计算结果」状态机（idle / computing / ready / stale / failed）。

#### 建议保留

- 侧边栏、页面标题区（返回工具箱）与既有导航/确认机制。
- 真实 FFmpeg 编码循环与预算规则：短样本 → 首次完整编码 → 最多一次宽度校正 → 非覆盖发布；帧率与截取时长不被改动，8,000,000 字节硬上限。
- 官方 asset 协议单文件授权、非覆盖保存（重名追加 `_2`）、取消语义、代次防护。
- 四种输出倾向的语义与各自帧率默认值（均衡 10 / 帧率优先 15 / 画质优先 8 / 自定义自由填写）。

#### 交给成熟库的部分

- 视频解码/播放、GIF 编码、文件对话框、路径 reveal、图片缩放平移复用 `PreviewViewport`；本轮没有新增自研编解码、播放器、队列或任务框架。

#### 最小修改方案

- 页面固定为四区：顶部工具行（导入/更换视频 + 文件名 + 引擎状态）、主预览（唯一的 GIF 结果，`PreviewViewport` 适应/1:1/放大/平移）、蓝色原片条（136px 缩略图 + 时间轴/播放头/双把手 + 播放 + 单计算按钮 + 时间输入）、右侧固定 300px 设置面板（2×2 倾向、帧率、尺寸、结果、保存、说明折叠）。
- 计算阶段不再要求导出目录：新增后端命令直接产出真实 GIF 到应用管理的临时目录；保存阶段只接受 taskId，复制同一份字节写入用户目录。
- 新增内容版本号：只有素材、截取范围、倾向/帧率/尺寸递增；播放、暂停、移动播放头、缩放平移不递增。播放头/播放/缩放不再使结果过期。

#### 明确不做

- 不做视觉稿，不做像素级视觉结论，不新增面板/设置页/依赖/队列/编码器；不缩帧率、不改截取时长、不放大、不写出超限文件、不覆盖用户已有文件。
- 不改侧边栏、图片压缩、Logo/版式/水印、Windows sidecar、更新/签名/发布链路。

#### 包体影响

- 无新增依赖、无新增 sidecar；只有前端代码/CSS 变化，产物字节见下方验证表。

#### 验收场景

- 导入视频 → 拖时间轴/改输入框截取 → 选倾向 → 计算：主预览出现真实 GIF，可放大/1:1/平移；不出现导出目录弹窗。
- 改倾向/帧率/宽度/区间：结果标为过期，保存禁用，计算按钮变「重新计算」。
- 播放、暂停、seek、缩放、平移：结果仍可保存。
- 计算中点「取消计算」：显示「已取消计算」，无结果、无导出文件。
- 保存：首次选目录，成功后再保存复用；同名追加序号；保存复用已计算结果，不重新编码。
- 换素材（计算中）走确认对话框；换素材后旧结果文件被清理。
- 预览失败（无 Tauri 运行时/asset 加载失败）：结果仍可保存。

### 实现要点

#### 后端（`src-tauri/src/media.rs`、`src-tauri/src/lib.rs`）

- 新增 `compute_gif_media_preview`：复用既有 `run_gif_task_loop`（同一条短样本 → 预算 → 完整编码 → 宽度校正 → 非覆盖发布路径），只把发布目录换成应用管理的临时目录 `std::env::temp_dir()/brand-material-gif-preview`，不写用户目录、不要求先选导出目录。
- `compute_gif_preview_file(...)` 在编码循环结束后读取终态事件，校验结果路径必须位于受控临时目录、必须存在且非空、必须以 `GIF` 开头、必须 ≤ `MAX_GIF_BYTES`（8,000,000 B），再用 FFprobe（新增可复用的 `probe_video_size`）读真实宽高；FFprobe 读不到时宽高返回 0，由前端 `<img>` 的 `naturalWidth/naturalHeight` 校正。返回值含 taskId/path/bytes/width/height/fps/duration/start/end。
- 新增 `ComputedGifRegistry`（managed state）：taskId → 临时文件 + 建议文件名（`{原名}_gif.gif`）。`lib.rs` 注册 `.manage(media::ComputedGifRegistry::default())` 与三个命令。
- 新增 `save_computed_gif(taskId, directory)`：只按 taskId 查登记表，校验目标目录，复制到同目录隐藏临时文件 → `sync_all` → 复用 `persist_gif_final` 做非覆盖发布（同名 `_2`/`_3`），返回最终路径与真实字节。**没有**接受任意源路径的复制接口，也不重新编码。
- 新增 `discard_computed_gif(taskId)`：删除该结果及其同前缀中间产物；计算失败/取消/参数变化后的结果文件也会被清理，避免临时目录增长。
- 新增 `prune_computed_gifs(dir, max_age)`：每次计算前清理 24 小时前的残留 GIF，只作用于应用临时目录。
- 取消：命令在启动前注册取消令牌（`MediaTaskRegistry::register_cancel_token`），使 `cancel_gif_media_task` 在两次 FFmpeg 子进程之间也能生效；取消统一映射为 `计算已取消`，不产生可保存结果。
- 临时目录/文件名由后端决定，前端只能传 taskId 与编码参数；`tauri.conf.json` 的 asset 协议静态 scope 仍为空，计算结果通过单文件授权供主预览读取。

#### 前端（`src/gif-tool/GifTool.vue`、`src/gif-tool/gifTool.css`）

- 布局：`.gif-tool` 为 `grid-template-columns: minmax(0,1fr) 300px; grid-template-rows: auto minmax(0,1fr)`；工具行跨两列；左列 `.gif-workspace` 为 `minmax(0,1fr) 180px`，主预览吃掉剩余高度；`.gif-transport` 固定 180px，内部 `grid-template-columns: 136px minmax(0,1fr)`，控制区行 `minmax(36px,1fr)` + 自动行，播放/计算行 `auto minmax(0,1fr) 112px`；右栏固定 300px、`overflow-y:auto`。窄窗口只收窄到 272px/120px，不退化成上下堆叠卡片。
- 顶部工具行：导入/更换视频按钮 + 文件名（`title` 显示完整路径，单行省略） + 引擎状态 + 提示；页面标题区的「返回工具箱」仍由 React `ToolPageHeader` 提供，不在 Vue 内重复。
- 主预览：唯一的 `<img>` 真实 GIF 放在共享 `PreviewViewport`（适应/1:1/最多 400%/抓手平移，`draggable=false`）；新结果或尺寸变化时 viewport 自动复位。预览失败只显示提示，不清空结果、不禁用保存。
- 蓝色原片条：136px `<video>` 缩略图（无原生 controls、`preload="metadata"`、`playsinline`），时间轴含选区、播放头（红）与起点/终点把手（蓝）；播放/暂停、`时间 / 总长`、选中时长、唯一「计算 GIF」按钮（计算中变为「取消计算」）、开始/结束数值输入与「重置片段」。
- 播放规则：播放头在选区外时从起点开始；到终点自动暂停；再次播放仍从起点开始。播放/暂停/seek 只更新播放头，不启动编码、不使结果过期。
- 键盘：时间轴可聚焦（role=slider + aria-valuemin/max/now），方向键移动播放头，Shift+方向键调起点，⌘/Ctrl+方向键调终点，Home 回到起点；播放/把手/按钮都有明确 aria-label。
- 设置面板：2×2 倾向按钮（42px 高、完整文案、`role=radio`/`aria-checked`，不换行）；非自定义倾向只给允许帧率档位、自动尺寸说明「尺寸自动调整，计算后查看实际结果」；自定义才出现输出宽度/最低宽度/帧率数字输入；结果块显示真实尺寸/体积/片段/设置帧率；唯一「保存 GIF」按钮 + 保存反馈 + 显示位置；`<details>` 说明短样本、最多两次完整编码、清理与失败语义。
- 状态机与代次：`contentRevision` 只由素材/范围/倾向/帧率/尺寸递增；计算结果记录产生它的 revision，过期为 stale（保留画面、保存禁用、提示重新计算）。计算请求携带 `computeTicket` + revision，返回时校验卸载/代次/版本，过期结果立即 `discardComputedGif` 且不显示。计算中再点主按钮 = 取消；不启动第二个同参数任务。
- 保存：只接受当前 revision 的结果快照；首次保存才弹目录，取消目录不缓存，成功后才缓存；目录弹窗等待期间结果/素材/参数变化则取消本次保存并提示；成功后显示路径并可通过既有 reveal 能力定位；同名由后端非覆盖追加。保存不重新编码。
- 换素材/卸载/返回工具箱：计算中更换素材或退出走确认对话框，确认后先取消 FFmpeg，再清理旧结果文件；卸载时同样清理，不把正在运行的编码留在后台。

## 九、复核修复：卸载清理 / 取消竞态 / 保存串台（2026-10-19）

Codex 复核在主流程通过后指出 3 组收尾问题，并在仓库外补了 4 条边界用例复现失败。本轮只修这 3 组、把 4 个场景补进正式测试，保留既有正常流程断言；未改其他功能，未打包、未提交、未推送、未发布。

### 问题与修复

1. **页面卸载没有完整清理任务和监听器**
   - 卸载时若仍有计算在跑，先按 taskId 调用后端 `cancelTask`，再清空计算/取消中状态并清理结果文件；不再把正在运行的 FFmpeg 留在后台。
   - `onMounted` 中每次 `await` 之后都检查 `unmounted`：晚到的 `listenTaskEvents` / `listenDroppedPaths` 解除函数在拿到后立即执行并终止后续初始化（不注册拖入回调、不请求引擎状态）。
   - 拖入回调在已卸载实例上直接忽略；两个解除函数执行后置空，避免重复调用。

2. **点击取消后，晚到的成功结果仍会显示并允许保存**
   - 前端按 taskId 记录取消意图：`cancellingTaskIds`（逻辑集合）+ `cancellingTaskId`（界面状态）。取消后原计算 Promise 即使成功返回，也会丢弃结果、调用 `discardComputedGif` 清理临时文件、显示「已取消计算」，不出现预览且保存保持禁用。
   - 任务真正结束前保持「取消中…」状态并禁用主计算按钮，避免并行启动下一次编码；参数变化导致的结果仍优先提示「参数已变化，本次计算结果已丢弃」。
   - 后端在最终登记结果前先取取消标记：已接受的取消 → 清理结果文件 → 返回 `计算已取消`，不登记为可保存结果、不返回成功。

3. **旧视频保存完成后污染新视频的保存状态**
   - 保存成功/失败回写界面前都校验发起保存时的 taskId 与内容版本；不匹配则丢弃回写（已成功落盘的旧文件保留，但不显示成新素材的保存结果）。
   - 换素材、清空结果、参数变化时同时清空保存提示、错误与路径。

### 新增测试

- 前端 `GifTool.compute.test.ts` 4 条：计算中卸载调用后端取消；监听注册未完成时卸载，晚到解除函数被立即执行且不再继续初始化；点击取消后原计算成功返回被丢弃并清理、期间保持取消中且不能并行计算；A 保存中换 B，A 保存晚归不显示「已保存」/路径。
